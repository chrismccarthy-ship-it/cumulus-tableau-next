# Manifests (sandbox → production)

All four files are generated by `python3 scripts/build_manifests.py` from the App Template tree, so member lists always match what the templates create.

| File | Metadata types | When to use it |
|---|---|---|
| `manifest_datakit.xml` | `DataKit` | The **data path**: a Data 360 data kit built in the source org (Data 360 Setup → Data Kits → New → add the Cumulus data streams, DLOs, DMO mappings and **semantic models**). Deploy this **first**; nothing below renders without the semantic models. Once created in the org, prefer the manifest Data 360 offers under *Download Manifest File* — it lists the kit's contents in dependency order. |
| `manifest_assets.xml` | `AnalyticsWorkspace`, `AnalyticsVisualization`, `AnalyticsDashboard` | The **asset path**: 7 workspaces, 65 visualizations, 7 dashboards. Deploy after the data kit. |
| `manifest_lwc.xml` | `LightningComponentBundle` | The four dashboard-extension LWCs. Deploy **before** `manifest_assets.xml` so the `c:cumulus*` widgets resolve when the dashboards are created. |
| `manifest_templates.xml` | `AppFrameworkTemplateBundle` | The **install-anywhere path**: the seven App Templates. Deploy, then create the app (`scripts/install_template.py` or `sf orchestrator app create`). This is also what goes in the 2GP package (`packaging/`). |

## The two ways to move Cumulus to another org

```
A. Data kit + assets (what "Use CLI to Deploy Tableau Next Assets from Sandbox to Production" describes)
   sf org login web -a sandbox      sf org login web -a prod
   sf project retrieve start --manifest manifests/manifest_datakit.xml -o sandbox
   sf project retrieve start --manifest manifests/manifest_lwc.xml     -o sandbox
   sf project retrieve start --manifest manifests/manifest_assets.xml  -o sandbox
   sf project deploy start --manifest manifests/manifest_datakit.xml -o prod --wait 30
   (run the data streams in prod, or ingest with scripts/load_data.py — the kit ships structure, not rows)
   sf project deploy start --manifest manifests/manifest_lwc.xml     -o prod
   sf project deploy start --manifest manifests/manifest_assets.xml  -o prod
   scripts/verify.sh prod

B. App Template (what this repo does for demos; data + assets in one shot)
   sf project deploy start --manifest manifests/manifest_lwc.xml -o prod
   python3 scripts/install_template.py --org prod --template Cumulus_Insurance
```

`scripts/promote.sh sandbox prod` runs path A end to end; `.github/workflows/promote.yml` is the same thing as a pipeline.

Gotchas we hit: `<version>` must not exceed the target org's API version (this repo is 67.0); semantic model API names get a numeric suffix at creation (`…_Model_988`) — the data kit carries the real name, hand-written manifests must be read from the org (`GET /services/data/v67.0/ssot/semantic/models?`); dashboards deployed by metadata keep the extension widget definitions but the LWC must already exist in the target org or the widget renders as "component not found".
